## Winston and Morgan
The single centralized Winston logger emits JSON with timestamp, level, message and per-request identifier where available. Request IDs are generated by the server with `randomUUID()`, returned as `X-Request-ID`, and preserved for asynchronous operations using AsyncLocalStorage. The HTTP log contains method, `req.path` (without query), status and duration. Health requests are excluded from HTTP logs. Log metadata passes recursive sensitive-key redaction and credential-bearing URL redaction. Do not log request/response bodies or secrets elsewhere in application code.

## Redis
Redis is optional. Set `REDIS_URL` and optionally `CACHE_ENABLED=true` (default is enabled when `REDIS_URL` is present). Setting `CACHE_ENABLED=false` disables it. `CACHE_TTL_SECONDS` defaults to 30 and is clamped to 5–300 seconds. Redis client errors do not crash Express. Redis connection is asynchronous and has bounded reconnect attempts; failed Redis operations time out on the request path and MongoDB remains authoritative. A later process restart may be required if retry attempts are exhausted.

## Cache keys and invalidation
Only the product catalogue/detail endpoints use Redis, and requests carrying Authorization or Cookie bypass cache. Keys use `gazu:products:v<generation>:<sha256(path + sorted query)>`. The generation is stored at `gazu:catalogue:version`. Admin product creation, changes, deactivation, review creation/deletion and checkout inventory changes bump the version **after successful database commits**. Redis reconnect bumps generation to hide possibly stale values. An uncertain invalidation disables cache usage rather than serving known-stale data. A version check before writing prevents an in-flight old response from being stored under the current generation. Old keys expire automatically. This strategy invalidates all product caches rather than scanning Redis keys.

`X-Cache` meanings: `MISS` for a database response eligible for caching, `HIT` for Redis JSON, `BYPASS` when Redis disabled/unavailable or request personalized. Cached values have finite TTL. Admin and customer records, JWTs, OTPs, carts, orders and private APIs are never cached.

## Health
`GET /api/health` returns Mongo `up/down` and Redis `up/down/disabled`. Mongo is required; Redis is optional and its outage does not force an HTTP 503.

## macOS manual verification
1. Install dependencies with `npm ci` at project root and `npm run setup`.
2. Install Redis with `brew install redis`; start it using `brew services start redis`.
3. Confirm `redis-cli ping` returns `PONG`.
4. In `backend/.env`, set `REDIS_URL=redis://127.0.0.1:6379`, leave existing Mongo credentials untouched, and optionally set `CACHE_TTL_SECONDS=30`.
5. Start with `npm run dev` from the project root.
6. Run `curl -i http://localhost:8000/api/products` twice; expect `X-Cache: MISS` then `X-Cache: HIT` while Redis is connected (the first request after restart may have a brief BYPASS during connection).
7. Try `curl -i 'http://localhost:8000/api/products?page=2&limit=2'`; a separate response must be returned.
8. As admin, edit product price or stock, then repeat the same public GET; expect a fresh MISS with updated data.
9. Perform a COD test checkout in a **development/test account** and confirm the next public product GET reflects the updated stock. Repeating the same checkout request ID must not create a second order.
10. Stop Redis: `brew services stop redis`. Repeat product requests: status should remain successful when MongoDB is up and `X-Cache: BYPASS` (or MISS during a race). Restart Redis and confirm caching resumes; if reconnect attempts have been exhausted, restart the backend.
11. Inspect terminal output for one JSON HTTP log per non-health request and a matching `X-Request-ID`; ensure no passwords, OTPs, JWTs or credential URLs appear.
12. Test `GET /api/health`: Redis down should not by itself cause 503.

## Testing
`npm test --prefix backend`, `npm test --prefix frontend`, `npm test --prefix payment-service`, `npm run build --prefix frontend`. Backend integration tests must use disposable MongoDB replica sets and mocks for outbound emails; never point these tests at production Atlas. See `TESTING.md` for this environment's actual results.

## Limitations
The isolated Phase 4 cache unit tests cover keys, HIT/MISS, version invalidation, stale-flight protection, fallback, request IDs and sanitization. Full API integration and Redis reconnect timing require a running local Redis and MongoDB replica set. Concurrent writes across multiple application instances would benefit from explicit load testing before public deployment. Redis cache does not enforce stock correctness: the transaction-safe MongoDB checkout does.

## Phase 5 boundary
Docker/Compose deployment, gateway redesign and microservice work were intentionally not implemented in Phase 4.
